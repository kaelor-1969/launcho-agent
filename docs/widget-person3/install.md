# راهنمای نصب و بررسی ویجت

این تحویل، بخش فرانت‌اند را آمادهٔ بازبینی می‌کند. فرم کاتالوگ‌دار فعلی فقط در `local_mock` فعال است؛ اتصال رسمی، موجودبودن قالب برای ثبت‌نام و ساخت واقعی تأیید نشده‌اند. وابستگی‌ها در [dependencies.md](dependencies.md) ثبت شده‌اند.

## نصب روی میزبان

فایل‌های `frontend/` را با ساختار فعلی در مسیر `/widget/` سرویس ویجت ارائه کنید. فونت و تصاویر `assets/` نیز لازم‌اند. سرویس باید endpointهای موجود session/chat/review/confirm را طبق [قرارداد هسته](../core-api-contract.md) ارائه کند؛ صرفاً ارائهٔ فایل‌های استاتیک برای اتصال واقعی کافی نیست.

تگ زیر را یک‌بار در صفحهٔ میزبان قرار دهید؛ آدرس نمونه را با مبدأ سرویس خود جایگزین کنید:

```html
<script defer src="https://YOUR-WIDGET-HOST/widget/loader.js"
  data-theme="light" data-position="right"
  data-offset="24" data-mobile-offset="16"
  data-auto-open="false"></script>
```

با `data-auto-open="false"`، iframe و جلسه فقط پس از بازکردن گفتگو ساخته می‌شوند. مقدار پیش‌فرض کد، بازشدن خودکار است. باز و بسته‌کردن پنل همان iframe و حافظهٔ گفتگو را حفظ می‌کند. برای اندازهٔ دلخواه می‌توان `data-width="480" data-height="600"` افزود؛ اندازه با viewport محدود می‌شود. ظاهر قبلی با `data-interface="legacy"` در دسترس است. پارامتر `data-demo="true"` فقط برای نمایش مستقل است؛ نصب واقعی را به mock تبدیل نکنید.

پس از بارگذاری loader:

```javascript
LaunchoWidget.open();
LaunchoWidget.close();
LaunchoWidget.setTheme('dark'); // light / dark / auto
LaunchoWidget.configure({position: 'left', offset: 24, mobileOffset: 16});
```

iframe و API روی مبدأ سرویس ویجت قرار می‌گیرند؛ `data-api-url` نمی‌تواند API را به مبدأ دیگری منتقل کند. کلید API، توکن جلسه یا اطلاعات پرداخت را در تگ نصب نگذارید. HTTPS برای نصب عملیاتی لازم است.

در سایت دارای CSP، مبدأ ویجت باید در `script-src` و `frame-src` مجاز باشد؛ استایل داخل Shadow DOM نیز باید با سیاست سایت سازگار باشد. سرور iframe باید `frame-ancestors` مناسب میزبان را به‌صورت header واقعی بفرستد؛ `X-Frame-Options: SAMEORIGIN` نصب روی مبدأ متفاوت را مسدود می‌کند. این تنظیمات سرور در این تحویل تغییر نکرده‌اند.

پس از انتشار، فایل loader و سند HTML باید نسخهٔ تازه را بگیرند؛ query نسخهٔ نصب میزبان را به‌روز کنید یا کش/CDN را طبق تنظیمات استقرار خود باطل کنید. query ماژول‌های HTML برای تغییرات این تحویل به‌روز شده است. نسخهٔ ذخیره‌شدهٔ قدیمی loader قابلیت هشدار refresh جدید را ندارد.

## تأیید، شبکه و refresh

ذخیره و مرور، پیش‌نویس نمی‌سازند. فقط فعال‌کردن صریح دکمهٔ تأیید اجازهٔ ارسال می‌دهد. دوبار کلیک یا Enter هنگام ارسال، درخواست دیگری نمی‌فرستد. retry پیام همان `requestId` و retry تأیید همان review را نگه می‌دارد؛ کلید idempotency عملیات را سرور مدیریت می‌کند.

پس از نتیجهٔ نامعلوم، ویرایش قفل است و دکمهٔ «بررسی نتیجهٔ همان درخواست» همان تأیید را دوباره می‌فرستد. در این وضعیت صفحه را تازه نکنید. میزبان با دریافت پرچم pending از iframe معتبر، هشدار خروج مرورگر را درخواست می‌کند؛ توکن یا بدنهٔ تأیید به میزبان داده نمی‌شود.

این هشدار تضمین بازیابی نیست: بستن اجباری، خاتمهٔ مرورگر/سیستم، محدودیت مرورگر موبایل، refresh خود iframe یا قبول خروج می‌تواند حافظه را از بین ببرد. توکن‌ها در `localStorage` یا `sessionStorage` نگهداری نمی‌شوند. refresh پس از نتیجهٔ قطعی، جلسهٔ خالی تازه می‌سازد و هیچ تأییدی را خودکار تکرار نمی‌کند. اگر نتیجهٔ قبلی گم شد، پیش از ساخت دوباره از پشتیبانی لانچو پیگیری کنید؛ بازیابی پایدار به قرارداد جداگانه نیاز دارد.

لینک ادامه فقط از پاسخ ساختاریافته و مقصد مجاز ساخته می‌شود و در تب تازه با `noopener noreferrer` باز می‌شود. بررسی وضعیت یک GET مستقل است؛ خطای آن ساخت را تکرار نمی‌کند. با گزارش انقضا، لینک همان کارت غیرفعال می‌شود. پیش‌نمایش محلی با برچسب آزمایشی، مقصد رسمی مشتری نیست.

## اعتبارسنجی بدون عملیات واقعی

از ریشهٔ مخزن با Node دارای WebSocket سراسری و Chrome نصب‌شده اجرا کنید؛ این محیط با Node 24.20.0 بررسی شده است:

```powershell
node tests/widget_quality_check.cjs
```

این دستور VM، فرم‌ها و آزمون session/loader را با پاسخ‌های کنترل‌شده اجرا می‌کند و با اولین خطا متوقف می‌شود. نیاز به سرور قبلی، npm install، مدل یا API ساخت واقعی ندارد. مسیر اجرایی مرورگر با متغیر `CHROME_PATH` و پوشهٔ خروجی با `WIDGET_ARTIFACT_DIR` قابل تعیین است. runner در صورت تعیین پوشهٔ مشترک، گزارش‌ها را در زیرپوشه‌های جداگانهٔ `signup/` و `sessions/` نگه می‌دارد.

بررسی مجدد صفحات عمومی، جداگانه و با دسترسی اینترنت است:

```powershell
node tests/widget_catalog_audit.cjs
node tests/widget_public_previews_browser.cjs
```

این دو دستور فقط خواندنی‌اند و گزارش تاریخ‌دار کاتالوگ را در همین پوشه به‌روز می‌کنند. پاسخ HTTP و رندر نمونه، موجودبودن قالب برای ثبت‌نام را ثابت نمی‌کنند. نتیجهٔ قبلی ۲۳/۲۳ بود؛ برای تحویل دوباره بدون نیاز، درخواست عمومی را تکرار نکنید.

گزارش مرورگرهای بررسی‌شده در [browser-coverage.md](browser-coverage.md)، شواهد در [evidence.md](evidence.md) و متن آمادهٔ PR در [pr-ready.md](pr-ready.md) است. پس از دو دور بازبینی موفق، فقط push شاخهٔ اختصاصی با مجوز کاربر انجام می‌شود؛ ساخت PR، merge و deployment مجاز نیست.

## نکات بازبینی پیش از push

فیلد «دامنهٔ موجود» طبق قرارداد داخلی پشتیبانی می‌شود؛ با پرکردن آن نام و پسوند دامنهٔ تازه غیرفعال می‌شوند. پس از انقضای جلسه و شروع جلسهٔ تازه، فرم از ترجیحات همان جلسه بازسازی می‌شود. کاتالوگ عمومی mock عمداً گزینهٔ تأییدشده ندارد؛ آزمون‌های کنترل‌شده از content/launcho-widget-catalog.json فقط به‌عنوان fixture آزمایشی استفاده می‌کنند.

برای اجرای مجموعهٔ Python موجود در ویندوز، PYTHONUTF8=1 را در فرایند تست تنظیم کنید تا فرایندهای فرزند هم UTF-8 بخوانند؛ اجرای نهایی با همین تنظیم162تست موفق داشت. کد Python در این تحویل تغییر نکرده است.

# قرارداد mock با پیش‌نویس پایدار — نسخهٔ ۲

> مسیر پیشنهاد مالی اکنون مرحله‌های نام‌دار و خروجی ساختاریافته دارد؛ مرجع جاری آن [قرارداد پیشنهاد](financial-offers-stage5.md) و نمونه‌های `examples/launcho-mock-v3.json` است. رفتار پیش‌نویس نسخهٔ ۲ تغییر نکرده است.

نسخه `local-mock-v2.0.0`، تاریخ ۲۰۲۶-۱۱-۱۲. این قرارداد داخلی آزمون است، نه قرارداد رسمی لانچو. مرجع فعلی ساخت و خواندن پیش‌نویس این سند است؛ [نسخهٔ ۱](launcho-mock-contract-v1.md) سابقهٔ طراحی و جزئیات چهار مسیر قبلی را نگه می‌دارد.

## محدودهٔ این تحویل

ساخت، ذخیره و پیگیری پیش‌نویس در `app/mock_launcho.py` و `app/mock_draft_store.py` پیاده شده‌اند. هستهٔ جلسه، schemaهای مشترک، routeهای اصلی، ویجت و تنظیمات استقرار تغییر نکرده‌اند. `LocalMockGateway.can_create` همچنان false است: موفقیت mock نباید به‌عنوان ساخت واقعی به هسته یا مشتری گزارش شود. لینک‌های این نسخه فقط به صفحهٔ کنترل‌شدهٔ خود mock می‌روند؛ لینک رسمی لانچو از روی ref اختراع نمی‌شود.

## اجرا و جداسازی داده

mock کلید مدل نمی‌خواهد و با Python 3.10 یا جدیدتر اجرا می‌شود؛ آزمون این تحویل روی 3.12 است. محیط مجازی و نصب requirements از قبل لازم است. اجرای بدون متغیرهای زیر، کاتالوگ پیش‌فرض خالی را حفظ می‌کند؛ برای ساخت موفق، پروفایل مصنوعی test را صریح فعال کنید.

macOS / Linux، از ریشهٔ مخزن:

```sh
LAUNCHO_MOCK_DRAFT_CATALOG=test \
LAUNCHO_MOCK_DB=data/mock-drafts-development.sqlite3 \
python -m uvicorn app.mock_launcho:app --host 127.0.0.1 --port 8001
```

PowerShell:

```powershell
$env:LAUNCHO_MOCK_DRAFT_CATALOG = 'test'
$env:LAUNCHO_MOCK_DB = 'data/mock-drafts-development.sqlite3'
python -m uvicorn app.mock_launcho:app --host 127.0.0.1 --port 8001
```

| متغیر مختص mock | پیش‌فرض و معنا |
| --- | --- |
| `LAUNCHO_MOCK_DB` | `data/mock-drafts.sqlite3` در ریشهٔ پروژه؛ مستقل از دیتابیس جلسه |
| `LAUNCHO_MOCK_DRAFT_CATALOG` | unavailable؛ فقط unavailable یا test |
| `LAUNCHO_MOCK_DRAFT_TTL_SECONDS` | 86400؛ عمر پیش‌نویس، ثانیهٔ صحیح مثبت |
| `LAUNCHO_MOCK_KEY_RETENTION_SECONDS` | 604800؛ عمر کلید و نتیجه، حداقل برابر TTL |
| `LAUNCHO_MOCK_PREVIEW_ORIGIN` | `http://127.0.0.1:8001`؛ فقط HTTP loopback با پورت معتبر، بدون مسیر/credential/query/fragment |

عمر یک‌روزه و نگهداری هفت‌روزه پیش‌فرض فنی همین شبیه‌سازند تا فاصلهٔ انقضا و مهلت بازیابی وجود داشته باشد؛ سیاست مصوب سرویس واقعی نیستند. مقدار زمان‌ها هنگام ایجاد هر رکورد تثبیت می‌شود؛ تغییر تنظیمات پس از restart رکورد قبلی را تمدید نمی‌کند. اگر پورت mock عوض شود، origin را برای لینک‌های رکوردهای جدید هم تنظیم کنید. لینک ذخیره‌شدهٔ رکورد قبلی تغییر نمی‌کند.

آزمون‌ها همیشه `TemporaryDirectory` و مسیر دیتابیس اختصاصی می‌سازند؛ دیتابیس اجرای معمول را باز یا پاک نمی‌کنند. فایل کاتالوگ test در `content/launcho-draft-test-catalog.json` جداست؛ همهٔ گزینه‌های آن `test_only` هستند. در حالت test، `/signup-options` همین دادهٔ مصنوعی را با هشدار می‌دهد؛ کاتالوگ عمومی موجود بازنویسی نشده است.

## مسیرها و پوشش پاسخ

| مسیر | نتیجه |
| --- | --- |
| `POST /signup-drafts` | ایجاد یا بازیابی همان نتیجهٔ قبلی، HTTP 200 |
| `GET /signup-drafts/{ref}` | خواندن با توکن، HTTP 200؛ منقضی نیز status=expired |
| `GET /mock-drafts/{ref}` | صفحهٔ ثابت و صریحاً آزمایشی؛ 200 فعال، 410 منقضی، 404 ناموجود |

دو مسیر API هدر `Authorization: Bearer local-simulation` می‌خواهند. ایجاد هدر `Idempotency-Key` نیز می‌خواهد: 16 تا 128 کاراکتر از `[A-Za-z0-9_-]`. کلید دادهٔ شخصی نباشد. مقصد preview بدون توکن باز می‌شود، اما فقط متن ثابت وضعیت دارد؛ نام، payload، مبلغ و اطلاعات ثبت‌شده را نمایش نمی‌دهد. این لینک فقط امکان مشاهدهٔ وجود و وضعیت یک پیش‌نویس آزمایشی را می‌دهد و پرداخت یا ادامهٔ ثبت‌نام واقعی ندارد.

پاسخ API موفق:

```json
{
  "ok": true,
  "simulation": true,
  "notice": "داده‌های این API آزمایشی‌اند. قیمت‌های نمونه نباید به مشتری نمایش داده شوند و جشنواره برای خرید معتبر نیست.",
  "data": {
    "ref": "sd_mock_example01",
    "status": "draft",
    "createdAt": "2026-11-12T12:00:00+00:00",
    "expiresAt": "2026-11-13T12:00:00+00:00",
    "retainUntil": "2026-11-19T12:00:00+00:00",
    "confirmUrl": "http://127.0.0.1:8001/mock-drafts/sd_mock_example01",
    "quote": {"currency": "toman", "total": 17400000, "isFinal": false}
  }
}
```

شناسه و زمان‌های این مثال توضیحی‌اند؛ اجرا شناسهٔ تصادفی تازه می‌سازد. ref از الگوی `sd_[A-Za-z0-9_-]{4,128}` پیروی می‌کند. زمان‌ها UTC با timezone هستند. همهٔ فیلدهای بالا اجباری‌اند؛ quote می‌تواند null باشد. تنها وضعیت‌های قابل تولید mock، draft و expired هستند.

## ورودی معتبر و نمونهٔ درخواست

ساختار درخواست در [schema مشترک آداپتور](examples/launcho-draft-request.schema.json) و قواعد `normalize_draft` است. نام کسب‌وکار، صنف، دوره، قالب و domain اجباری‌اند؛ kind پیش‌فرض shop است. نوع خدمت فقط shop/website؛ دوره دقیقاً int از 3، 6، 12؛ نام 1 تا 80 و شناسه‌ها 1 تا 100 کاراکتر پس از trim. فیلد اضافی و اطلاعات حساس مطابق قواعد مشترک رد می‌شوند.

```sh
curl -X POST 'http://127.0.0.1:8001/signup-drafts' \
  -H 'Authorization: Bearer local-simulation' \
  -H 'Idempotency-Key: mock_request_example_01' \
  -H 'Content-Type: application/json' \
  -d '{"kind":"shop","businessName":"فروشگاه آزمایشی","category":"test-category","planMonths":3,"template":"test-template","domain":{"label":"example","tld":"ir"}}'
```

برای website شناسه‌ها `test-website-category` و `test-website-template` هستند. دامنه یا `{label,tld}` از پسوندهای fixture است یا `{ownDomain}`؛ ترکیب دو شکل رد می‌شود. صنف و قالب و دوره و پسوند برای عملیات جدید اعتبارسنجی می‌شوند؛ قالب unavailable پذیرفته نیست.

قیمت نمونه از setup + plan + annualFee محاسبه می‌شود؛ shop با 3 ماه و ir برابر 17400000 و website برابر 7400000 تومان نمونه است. برای ownDomain هزینهٔ اتصال معلوم نیست؛ quote=null برمی‌گردد، نه صفر یا قیمت حدسی. هیچ‌یک تعرفهٔ زنده نیستند.

## قواعد تکرار، انقضا و نگهداری

1. احراز هویت و شکل کلید/JSON/فیلدها بررسی می‌شوند؛ درخواست نامعتبر هیچ رکوردی نمی‌سازد.
2. payload طبق `normalize_draft` نرمال می‌شود: trim رشته‌ها، kind پیش‌فرض، حذف جایگزین‌های null دامنه؛ فیلد اجباری null رد می‌شود. تبدیل حروف دامنه انجام نمی‌شود. JSON با کلیدهای مرتب مقایسه می‌شود؛ ترتیب کلیدها مهم نیست.
3. کلید معتبر با SHA-256 در دیتابیس نگهداری می‌شود؛ دامنهٔ کلید تمام عملیات ساخت همین دیتابیس mock است، نه یک جلسهٔ مرورگر.
4. تا پایان retention، کلید یکسان و payload یکسان پیش از انقضا دقیقاً همان result قبلی را می‌دهد: ref، مبلغ، لینک و زمان‌ها تغییر نمی‌کنند.
5. کلید یکسان و payload متفاوت معتبر 409 است، حتی اگر پیش‌نویس قبلی منقضی شده باشد. payload از نظر شکلی نامعتبر 422 است.
6. در `now >= expiresAt`، تکرار payload قبلی با همان کلید 410 است؛ GET همان ref تا پایان retention با HTTP 200 و status=expired برمی‌گردد. لینک preview در انقضا HTTP 410 دارد.
7. فقط برای کلید جدید، موجودی کاتالوگ بررسی می‌شود؛ حذف بعدی قالب مانع بازیابی نتیجهٔ قبلی نیست.
8. کلید، payload و result در یک تراکنش `BEGIN IMMEDIATE` با SQLite و synchronous=FULL ثبت می‌شوند. دو درخواست هم‌زمان از نمونه‌های مستقل روی همان دیسک، یک برنده دارند؛ درخواست همسان نتیجهٔ همان برنده و درخواست متفاوت تعارض می‌گیرد.
9. شکست ذخیره پیش از commit باعث rollback می‌شود. از دست رفتن پاسخ پس از commit با ارسال همان کلید و بدنه بازیابی می‌شود؛ خطای شبکه/ذخیره مجوز عوض‌کردن کلید نیست.
10. در `now >= retainUntil` رکورد قابل حذف است؛ خواندن شناسهٔ حذف‌شده 404 است. پس از حذف، استفاده از کلید قبلی یک عملیات تازه با ref تازه محسوب می‌شود. مصرف‌کننده نباید بیرون مهلت نگهداری، retry را بدون خطر تکرار فرض کند.

پاکسازی در عملیات موفق خواندن/ساخت انجام می‌شود؛ `MockDraftStore.cleanup()` پاکسازی صریح و قابل‌آزمون دارد. سرویس بیکار پاکسازی زمان‌بندی‌شده ندارد. فایل SQLite پس از restart حفظ می‌شود؛ روی دیسک موقت یا filesystem چند میزبان تضمین دوام نداریم. این پیاده‌سازی دیتابیس جلسه را دستکاری نمی‌کند.

## خطاهای مسیرهای جدید

```json
{
  "ok": false,
  "error": {"code": "idempotency_conflict", "message": "این کلید قبلاً برای اطلاعات دیگری استفاده شده است."},
  "simulation": true,
  "notice": "داده‌های این API آزمایشی‌اند. قیمت‌های نمونه نباید به مشتری نمایش داده شوند و جشنواره برای خرید معتبر نیست."
}
```

| HTTP | code | معنا |
| --- | --- | --- |
| 401 | unauthorized | توکن غایب یا نامعتبر |
| 422 | invalid_idempotency_key | کلید غایب یا خارج از الگو |
| 422 | invalid_request | JSON، نوع داده، فیلد یا اطلاعات نامعتبر |
| 422 | invalid_option | گزینهٔ ناموجود یا غیرفعال |
| 422 | incompatible_template | قالب موجود با صنف انتخابی سازگار نیست |
| 422 | invalid_reference | ref خارج از الگو |
| 409 | idempotency_conflict | همان کلید برای بدنهٔ دیگر |
| 410 | draft_expired | replay همان عملیات منقضی |
| 404 | draft_not_found | شناسهٔ ناموجود یا حذف‌شده پس از retention |
| 503 | draft_outcome_unknown | خطای SQLite یا دسترسی به مسیر فایل؛ نتیجه قطعی فرض نشود و همان درخواست تکرار شود |
| 503 | catalog_unavailable | کاتالوگ معتبر یا گزینهٔ قابل انتخاب موجود نیست؛ ساخت جدید انجام نمی‌شود |

پاسخ ساخت/خواندن و خطاها `Cache-Control: no-store` دارند. متن خطا مقدار ورودی ردشده یا جزئیات دیتابیس را بازتاب نمی‌دهد. خطاهای چهار مسیر قبلی برای سازگاری همان شکل FastAPI نسخهٔ ۱ را دارند.

## اختلاف نسخه و مرز ادغام

نسخهٔ ۲ مسیرهای قبلاً غایب را پیاده کرده و پاسخ mock را صریحاً از پاسخ عملیاتی هسته جدا می‌کند: لینک loopback، quote احتمالاً null و retainUntil متعلق به mock هستند. هستهٔ فعلی لینک loopback را رد می‌کند؛ اعتبارسنجی آن ضعیف نشده و ساخت mock از طریق هسته فعال نشده است. آزمون‌های بخش قبل همچنان مرز اصلی هسته و آداپتور رسمی را با پاسخ کنترل‌شده می‌آزمایند. برای ادغام نهایی، نفر اول و نفر دوم باید مرز adapter آزمایشی را مشترک تعیین کنند؛ هیچ موفقیت واقعی از این mock استنباط نشود.

[نمونه‌های HTTP جاری](examples/launcho-mock-v2.json) با TestClient و دیتابیس موقت تولید می‌شوند. نمونهٔ پاسخ رسمیِ فایل `launcho-draft-target-v1.json` صرفاً fixture تاریخی تست هسته است و پاسخ این mock نیست.

[هشت سناریوی واقعی پیش‌نویس](examples/launcho-mock-drafts-v2.json) شامل ایجاد، replay، تعارض، وضعیت فعال، replay منقضی، وضعیت منقضی، حذف پس از retention و شناسهٔ نامعتبر است. این نمونه‌ها با ساعت ثابت و SQLite موقت از پاسخ API تولید و در تست دوباره مقایسه می‌شوند؛ شناسهٔ ثابت فقط در تولید نمونه‌ها تزریق شده است. تولید مجدد: `python tests/export_launcho_contract.py`.

## آزمون

```sh
python -m unittest discover -s tests -p test_mock_drafts.py -v
python -m unittest discover -s tests -v
```

آزمون‌های این بخش شامل ساخت و خواندن، replay نرمال‌شده، تعارض، هم‌زمانی با appهای مستقل، قطع پاسخ پس از commit، rollback، بازیابی در پردازش تازه، تغییر تنظیمات پس از restart، مرز دقیق TTL و retention، مقصد آزمایشی، خطاهای ورودی و جداسازی داده‌اند. مدل و API واقعی فراخوانی نمی‌شوند.

نتیجه در ۲۰۲۶-۱۱-۱۲ با Python 3.12.16: هر 106 آزمون پایتون موفق، شامل 16 آزمون `test_mock_drafts.py`. علاوه بر آن، یک سرور واقعی uvicorn با پورت loopback و دیتابیس موقت اجرا شد؛ ساخت، بازشدن مقصد آزمایشی، توقف کامل پردازش، راه‌اندازی مجدد، دریافت همان result، پیگیری وضعیت و تعارض 409 موفق بودند و دیتابیس فقط یک رکورد داشت. سرور و دادهٔ این بررسی پس از اتمام حذف شدند. بررسی قطعی پس از commit در تست با قطع تولید پاسخ HTTP شبیه‌سازی شده است؛ قطع فیزیکی شبکه ادعا نمی‌شود.

بازبینی دوم همان روز: سه ایراد اصلاح شد و هر 109 آزمون، شامل 19 آزمون همین بخش، موفق شد. مسیر نامناسب یا غیرقابل‌دسترسی دیتابیس به‌جای خطای عمومی 500 پاسخ امن 503 می‌دهد؛ تنظیم origin نامعتبر، از جمله پورت صفر، پیش از دسترسی به دیتابیس رد می‌شود؛ schema بدنهٔ ساخت در OpenAPI و `/docs` نیز موجود و ارجاع‌های آن قابل‌حل است. تست‌ها هم‌زمانی، ماندگاری و قرارداد قبلی را دوباره پوشش دادند؛ `git diff --check` بدون خطا بود.

پس از تکمیل مرحلهٔ کاتالوگ، [قرارداد کاتالوگ](launcho-catalog.md) مرجع metadata و قواعد انتخاب است. GET گزینه‌ها metadata نسخهٔ 1.0.0 را اضافه می‌کند. نبود کاتالوگ برای ساخت جدید از invalid_option (422) به catalog_unavailable (503) تفکیک شده است؛ شناسهٔ ناموجود در کاتالوگ معتبر همچنان 422 دارد. فهرست test همان فایل جداگانه است و هسته/ویجت تغییری نکرده‌اند. در آداپتور گزینه‌ها دیگر کش نمی‌شوند تا دادهٔ حذف‌شده یا قطعی با fallback پنهان نشود.

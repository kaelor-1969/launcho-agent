# تحویل هسته گفتگو و تأیید پیش‌نویس

این بخش، وظایف مدیر پروژه در تقسیم کار سه‌نفره را پیاده می‌کند. اتصال Vitaico، کلیدها، فایل .env، کد frontend و فایل launcho_api.py هم‌تیمی دوم تغییر نکرده‌اند. هیچ درخواست واقعی به مدل یا API لانچو برای آزمون این تغییر ارسال نشده است.

## چه چیزی آماده است

- جلسه پایدار در SQLite، تاریخچه محدود و اطلاعات غیرحساس قابل ویرایش.
- پیشنهاد اطلاعات توسط مدل با ابزار update_signup_preferences؛ مدل ابزار نوشتنی ندارد.
- پوشاندن شماره‌های رایج ایرانی، کدهای مشخص‌شده، رمز، کلید و ایمیل پیش از مدل و ذخیره.
- خلاصه متصل به revision، توکن مستقل تأیید و مسیر جداگانه برای رویداد دکمه.
- جلوگیری از تأیید قدیمی، کلیک همزمان، دسترسی جلسه دیگر و ارسال دوباره با کلید تازه پس از timeout.
- بررسی سخت‌گیرانه ref، وضعیت، انقضا و confirmUrl پاسخ API پیش از اعلام موفقیت.
- بازیابی جلسه مرتبط با signupRef فقط با قابلیت مالک همان جلسه.
- لینک عمومی جایگزین با فهرست پارامترهای مجاز؛ بدون دامنه یا اطلاعات هویتی.

## نکته اتصال مهم

این سند قرارداد داخلی پروژه است، نه قرارداد رسمی لانچو. factory در app/services/draft_gateway.py با LAUNCHO_MOCK_URL اتصال local_mock با can_create=True می‌سازد. آداپتور واقعی نیز موجود است؛ فعال‌سازی نوشتن آن نیازمند LAUNCHO_ENABLE_DRAFTS=1 است. تطبیق آن با قرارداد رسمی و سرویس واقعی تأیید نشده است. بدون تنظیم اتصال، حالت legacy_mock فقط خواندنی است.

آزمون‌های tests/test_conversation_core.py یک اتصال صریح test_mock با رفتار تکرار و انقضا دارند؛ مسیر کامل در همان آزمون اجرا شده است. آن fixture سرویس عملیاتی یا API واقعی نیست.

## قرارداد نفر اول و هسته

### ایجاد جلسه

POST /api/sessions بدون اطلاعات شخصی، پاسخ 201:

```json
{
  "sessionId": "opaque-session-id",
  "sessionToken": "owner-capability-returned-once",
  "revision": 0,
  "preferences": {"kind": "shop"},
  "history": [],
  "adapterMode": "local_mock",
  "canCreateDraft": true
}
```

از این به بعد X-Session-Token در header درخواست‌های همان جلسه ارسال می‌شود. توکن در URL، پیام مدل، لاگ یا صفحه میزبان قرار نگیرد. بدون آن، حتی دانستن sessionId یا signupRef اجازه خواندن گفتگو نمی‌دهد. نگهداری امن آن داخل origin خود ویجت و ادامه میان navigation با نفر اول هماهنگ شود؛ لودر حق خواندن storage میزبان را ندارد.

### گفتگو

POST /api/chat:

```json
{"sessionId":"opaque-session-id","message":"نام کسب‌وکار من نمونه است"}
```

پاسخ شامل reply، sessionId، revision، preferences و nextAction است. nextAction یا collect_preferences است یا review. این فقط راهنمای UI است و موفقیت ساخت نیست. مرورگر تاریخچه دلخواه به سرور نمی‌فرستد؛ تاریخچه معتبر از ذخیره سرور خوانده می‌شود. در هنگام درخواست، ورودی و تأیید همزمان قفل شوند.

بدون sessionId، قرارداد قدیمی {message} به {reply} حفظ می‌شود، ولی آن مسیر حافظه یا اختیار ساخت پیش‌نویس ندارد.

### ویرایش مستقیم انتخاب‌ها

PATCH /api/sessions/{sessionId}/preferences:

```json
{
  "revision": 0,
  "preferences": {
    "kind": "shop",
    "businessName": "نمونه",
    "category": "fashion",
    "planMonths": 3,
    "template": "example-row",
    "domain": {"ownDomain":"example.ir"}
  }
}
```

شناسه‌های مثال، fixture محلی‌اند؛ در رابط واقعی از catalog قرارداد استفاده شود. انتخاب دامنه جدید به شکل {label,tld} است و پسوند باید در پاسخ pricing موجود باشد. null فیلد را پاک می‌کند. تغییر kind، دسته و قالب قبلی را پاک می‌کند. هر تغییر واقعی revision را افزایش و تأیید قبلی را باطل می‌کند. فیلد mobile، ownerName، otp، password و هر فیلد خارج از schema رد می‌شود.

### خلاصه برای مرور

POST /api/sessions/{sessionId}/review:

```json
{"revision":1}
```

پاسخ reviewId، confirmationToken، revision، expiresAt، summary، estimate و canConfirm دارد. confirmationToken فقط داخل کنترل UI بماند و به مدل داده نشود. خلاصه از اطلاعات ذخیره‌شده سرور ساخته می‌شود. اگر اتصال زنده و داده کافی نباشد، estimate برابر null است؛ UI نباید آن را صفر یا قیمت قطعی نمایش دهد. حالت mock واضح نمایش داده شود.

### کلیک تأیید

فقط handler دکمه تأیید، POST /api/sessions/{sessionId}/confirm را بفرستد:

```json
{
  "revision":1,
  "reviewId":"review-id-from-server",
  "confirmationToken":"confirmation-token-from-server",
  "confirmed":true
}
```

در این مسیر اطلاعات یا مبلغ تازه از مرورگر پذیرفته نمی‌شود. payload از snapshot سرور خوانده می‌شود. عملیات با Idempotency-Key تولیدشده و ذخیره‌شده سرور انجام می‌شود؛ مدل این کلید را نمی‌بیند. دکمه در حال ارسال غیرفعال شود. اجرای این endpoint نشان‌دهنده قصد صریح کلاینت مجاز است؛ تشخیص سخت‌افزاری کلیک انسان انجام نمی‌شود.

در موفقیت HTTP 200، ref، confirmUrl، expiresAt، status=draft، adapterMode و replayed برمی‌گردند. quote در حالت محلی وجود ندارد؛ estimate نیز null است. در حالت واقعی quote.isFinal=false است. confirmUrl محلی مسیر /api/local-drafts/{ref}/preview در مبدأ خود سرویس است. لینک فقط از همین پاسخ ساخته شود. موفقیت نوشتنی از متن reply استخراج نشود.

اگر draft_outcome_unknown برگشت، نتیجه قطعی نیست. همان بدنه تأیید را نگه دارید و فقط با اقدام دستی همان درخواست را تکرار کنید. سرور همان کلید و payload قبلی را استفاده می‌کند. خلاصه یا عملیات تازه تا حل نتیجه نامعلوم ساخته نمی‌شود. برای دوام پس از refresh، UI باید علاوه بر قابلیت جلسه، بدنه pending تأیید را در فضای مجاز خود حفظ کند؛ توکن تأیید قابل بازخوانی از دیتابیس نیست. دوره نگهداری و روش ذخیره باید با سیاست داده لانچو هماهنگ شود.

### بازیابی و لینک جایگزین

- GET /api/sessions/{sessionId} با header مالک، تاریخچه، انتخاب‌ها و در صورت وجود draftState و draft را می‌دهد.
- POST /api/sessions/resume با {signupRef} و همان header مالک، جلسه مرتبط را برمی‌گرداند. ref به‌تنهایی کافی نیست.
- GET /api/sessions/{sessionId}/fallback-link?path=/ فقط لینک عمومی می‌دهد؛ isDraft=false. روی /start این مسیر رد می‌شود. path صرفاً زمینه رابط است، نه مجوز احراز یا عملیات.

## قرارداد هم‌تیمی دوم

آداپتور موجود این قرارداد داخلی را پیاده می‌کند؛ مالک اتصال باید سازگاری رسمی آن را تأیید کند:

```python
mode = "live"  # فقط برای اتصال واقعی
can_create = True
get_pricing() -> dict
get_signup_options(kind: str) -> dict
create_signup_draft(payload: dict, idempotency_key: str) -> dict
```

پاسخ موفق خام data یا پوشش ok/data پشتیبانی می‌شود. ساخت باید هدر Idempotency-Key دریافتی را بدون تغییر عبور دهد. خطای قطعی و بدون پذیرش عملیات با GatewayRejected(status,code) گزارش شود؛ timeout یا پاسخ نامطمئن نباید خطای قطعی محسوب شود. شناسه، بدنه و نتیجه تکراری باید از سمت لانچو قابل تضمین باشند؛ قفل محلی به‌تنهایی کافی نیست.

کش pricing و options، service-info، خواندن وضعیت، دامنه و قواعد خطای قرارداد در مالکیت همان adapter باقی می‌مانند. داده تاریخ‌گذشته نباید به‌عنوان mode=live برگردد. mock قدیمی هیچ‌گاه live علامت نخورد. این تحویل، آن اتصال را پیاده‌سازی نمی‌کند.

## خطاها

پاسخ خطا detail.code و detail.message امن دارد. 404 برای جلسه یا قابلیت مالک نامعتبر، 409 برای revision قدیمی/تأیید نامعتبر/درخواست در جریان، 410 برای انقضا، 422 برای اطلاعات نامعتبر و 503 برای سرویس یا نتیجه نامعلوم استفاده می‌شود. خطای قطعی adapter ممکن است وضعیت‌های قرارداد را برگرداند. خودکار retry نکنید و بدنه خطای upstream را نمایش ندهید.

## استقرار و محدودیت‌های باقیمانده

- .env و اتصال Vitaico دست‌نخورده‌اند؛ اجرای تست کلید آزمایشی تزریق می‌کند.
- LAUNCHO_SESSION_DB مسیر SQLite است؛ پیش‌فرض data/sessions.sqlite3. این پوشه وارد Git نشود.
- LAUNCHO_SESSION_TTL_SECONDS پیش‌فرض فنی ۸۶۴۰۰ ثانیه است، قابل تنظیم از ۶۰ تا ۸۶۴۰۰. این مقدار سیاست مصوب نگهداری داده نیست؛ پیش از انتشار تعیین شود. پاکسازی جلسات منقضی هنگام ایجاد جلسه جدید انجام می‌شود؛ برای زمان‌بندی دقیق‌تر کار دوره‌ای لازم است.
- تاریخچه حداکثر ۱۲ پیام دارد. این ذخیره‌سازی جای بازیابی دانش و خلاصه‌سازی بلندمدت را نمی‌گیرد.
- SQLite برای یک نمونه با دیسک پایدار است. روی Render بدون دیسک پایدار، restart یا redeploy می‌تواند جلسه و کلید تکرار را از بین ببرد؛ روی چند نمونه از این تنظیم استفاده نشود.
- مرورگر به session، chat، review و confirm متصل است؛ توکن‌ها فقط در حافظه iframe می‌مانند. اتصال ساخت واقعی همچنان به adapter قراردادی نیاز دارد.
- کنترل نرخ و هزینه عمومی، توکن اختصاصی و سیاست داده پیش از انتشار لازم‌اند؛ این تحویل آن‌ها را کامل معرفی نمی‌کند.
- ماسک داده، تشخیص رایج و مبتنی بر الگوست؛ تشخیص کامل همه شکل‌های اطلاعات شخصی ادعا نمی‌شود.
- آزمون‌های جدید، کد تأیید یا پرداخت واقعی ارسال نمی‌کنند؛ فقط mock قراردادی دارند.

## اجرای تست

از ریشه پروژه با محیط مجازی:

```cmd
venv\Scripts\python.exe -m unittest discover -s tests -v
```

تست قدیمی که ساخت مستقیم پیش‌نویس توسط مدل را انتظار داشت با آزمون منع ابزار نوشتنی جایگزین شده است. رفتارهای تأیید، replay، timeout، مالکیت، انقضا، persistence، redaction و قرارداد HTTP پوشش داده شده‌اند.

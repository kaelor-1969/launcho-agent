# قرارداد محلی API آزمایشی لانچو

> این سند تصویر تاریخی نسخهٔ ۱ است. از مرحلهٔ پیش‌نویس پایدار، [قرارداد نسخهٔ ۲](launcho-mock-contract-v2.md) مرجع رفتار جاری mock است؛ مسیرهای ساخت و خواندن پیش‌نویس اکنون پیاده شده‌اند. مثال لینک رسمی در این سند فقط fixture آزمون هسته است و پاسخ اجرایی mock نیست.

نسخه: `local-mock-v1.1.0` — تاریخ بررسی کد: ۲۰۲۶-۱۱-۱۲.

این سند قرارداد رسمی لانچو نیست. بخش «موجود» از کد فعلی استخراج شده و بخش «هدف پیش‌نویس» مشخصات محلی مرحلهٔ بعد است؛ مستندشدن آن به معنی پیاده‌سازی نیست. هیچ قیمت، قالب یا جشنوارهٔ آزمایشی مجوز خرید یا ثبت واقعی ایجاد نمی‌کند.

## محدوده و وضعیت

| عملیات | وضعیت در mock فعلی |
| --- | --- |
| `GET /pricing` | موجود |
| `GET /signup-options` | موجود، کاتالوگ معتبر فعلاً خالی |
| `GET /service-info` | موجود |
| `POST /offers/match` | موجود، پیشنهاد صرفاً آزمایشی |
| `POST /signup-drafts` | پیاده‌نشده؛ اکنون 404 |
| `GET /signup-drafts/{ref}` | پیاده‌نشده؛ اکنون 404 |

مرجع اجرا `app/mock_launcho.py`، مرجع داده `content/launcho-mock.json` و `content/launcho-public.json` و مرز مصرف `app/services/draft_gateway.py` است. این API با routeهای `/api/sessions` و `/api/chat` فرق دارد. هستهٔ جلسه، routeهای اصلی و ویجت در این مرحله تغییر نمی‌کنند.

## قواعد مشترک موجود

- آدرس اجرای محلی: `http://127.0.0.1:8001`. سرور فقط روی loopback اجرا شود.
- هدر مسیرهای داده: `Authorization: Bearer local-simulation`. این توکن ثابت صرفاً برای شبیه‌سازی است.
- بدنهٔ POST از نوع `application/json`؛ نام فیلدها به حروف کوچک و بزرگ حساس است.
- `kind` فقط `shop` یا `website` است.
- پاسخ موفق همهٔ مسیرهای موجود HTTP 200 و دارای این چهار فیلد است:

```json
{
  "ok": true,
  "data": {},
  "simulation": true,
  "notice": "داده‌های این API آزمایشی‌اند. قیمت‌های نمونه نباید به مشتری نمایش داده شوند و جشنواره برای خرید معتبر نیست."
}
```

`data` در هر مسیر ساختار زیر را دارد. آداپتور فعلی این پوشش را باز می‌کند؛ پس مصرف‌کننده نباید فقط به باقی‌ماندن `simulation` بعد از آداپتور اتکا کند. حالت اتصال باید `local_mock` بماند و هرگز `live` اعلام نشود.

نمونه‌های کامل درخواست و پاسخ در [فایل نمونه‌ها](examples/launcho-mock-v1.json) هستند. این فایل با `python tests/export_launcho_contract.py` از پاسخ HTTP درون‌پردازه‌ای TestClient ساخته می‌شود؛ شبکهٔ واقعی فراخوانی نمی‌شود. در 422 فقط type و loc قرارداد مقایسه‌اند. مقادیر fixture تعرفهٔ زنده نیستند.

## ۱. قیمت: موجود

`GET /pricing`، بدون بدنه. پارامتر اختیاری `kind` است؛ نبود آن پاسخ هر دو خدمت را برمی‌گرداند. `kind` نامعتبر 422 است.

| فیلد data | نوع و معنا |
| --- | --- |
| `currency` | رشتهٔ `toman`؛ همهٔ اعداد قیمت به تومان |
| `setupFees` | شیء با هزینهٔ نمونهٔ `shop` و `website` |
| `defaultSignupPlanMonths` | عدد صحیح؛ فعلاً 3 |
| `plans` | آرایهٔ `months`, `title`, `price`, `listPrice`, `featured`, `giftMonthly`؛ دوره‌های فعلی 3، 6، 12 |
| `domains` | آرایهٔ `tld`, `includedInSetup`, `annualFee` |
| `giftUsage` | `renewsMonthly` و `rollover` بولی، `uses` آرایهٔ رشته |
| `serviceDetails` | فقط بدون kind؛ شیء شامل `shop` و `website` |

جزئیات هر خدمت شامل `setupIncludes` و `planIncludes` (آرایهٔ رشته) و `installment` است. اقساط دارای `count` و `monthlyPart` عدد صحیح، `scope=setup_only` و `line` توضیحی است. این اعداد فقط نمونه‌اند.

با `GET /pricing?kind=website` یا `kind=shop`، فیلد `serviceDetails` حذف می‌شود و `kind` و جزئیات همان خدمت در ریشهٔ `data` قرار می‌گیرند. فیلدهای مشترک حفظ می‌شوند. بدون kind، اقساط مشترک در ریشه وجود ندارد؛ مصرف‌کننده نباید اقساط سایت و فروشگاه را یکی فرض کند.

```sh
curl -H 'Authorization: Bearer local-simulation' \
  'http://127.0.0.1:8001/pricing?kind=website'
```

## ۲. گزینه‌های ثبت‌نام: موجود

`GET /signup-options?kind=shop`؛ پارامتر `kind` اجباری و بدون بدنه است. نبود یا نامعتبر بودن آن 422 است. پاسخ فعلی داخل پوشش مشترک:

```json
{
  "kind": "shop",
  "availability": "unavailable",
  "notice": "گزینه‌های قابل ثبت تا دریافت دادهٔ مورد تأیید خالی‌اند؛ این فهرست نمایندهٔ گزینه‌های سایت واقعی نیست.",
  "steps": [],
  "businessCategories": [],
  "templateCategories": [],
  "templates": []
}
```

فهرست خالی پاسخ موفق با نبود داده است؛ خطای شبکه نیست و اجازهٔ حدس‌زدن شناسه نمی‌دهد. برای website همین ساختار با kind مربوطه برمی‌گردد. مصرف‌کنندهٔ هسته از صنف `id` و از قالب `id` و `available` می‌خواند؛ schema کامل کاتالوگ و وضعیت تأیید هر گزینه در مرحلهٔ کاتالوگ تکمیل می‌شود. نمونه‌های `fashion` و `example-row` در فایل قدیمی `launcho_api.py` کاتالوگ رسمی این mock نیستند.

## ۳. اطلاعات سرویس: موجود

`GET /service-info`؛ بدون پارامتر و بدنه. `data` شامل `contactUrl` (رشتهٔ لینک)، `useCases` (آرایهٔ رشته)، `overview` و `featureSummary` از فایل عمومی است؛ ساختار و مقادیر کامل در فایل نمونه‌ها ثبت شده‌اند. این مسیر API صحت‌سنجی یا به‌روزرسانی زندهٔ ادعاها نیست؛ منبع و تاریخ تأیید محتوا در content نگهداری می‌شود.

## ۴. تطبیق پیشنهاد: موجود

`POST /offers/match`؛ فیلد اضافی در بدنه رد می‌شود.

| فیلد | الزام و مقادیر |
| --- | --- |
| `kind` | اجباری؛ shop یا website |
| `planMonths` | اختیاری یا null؛ 3، 6، 12 |
| `step` | اجباری؛ عدد صحیح از 0 تا 4 |
| `objections` | آرایهٔ اجباری؛ اعضا از price، trust، complexity، time، template، domain، other |
| `needs` | آرایهٔ اجباری؛ اعضا از low_upfront، fast_launch، own_domain، support، other |
| `discountAlreadyShown` | بولی اجباری |

این جدول نوع‌های مورد انتظار مصرف‌کننده را بیان می‌کند؛ مدل فعلی Pydantic strict نیست و نباید ردشدن همهٔ شکل‌های قابل تبدیل را تضمین‌شده دانست. آرایهٔ خالی مجاز است. پارامتر query اضافی در مسیرهای موجود صریحاً منع نشده است.

```sh
curl -X POST 'http://127.0.0.1:8001/offers/match' \
  -H 'Authorization: Bearer local-simulation' \
  -H 'Content-Type: application/json' \
  -d '{"kind":"shop","planMonths":3,"step":4,"objections":["price"],"needs":["low_upfront"],"discountAlreadyShown":false}'
```

فقط وقتی kind برابر shop، مرحله برابر 4، اعتراض شامل price، نیاز شامل low_upfront و پیشنهاد قبلاً نمایش داده نشده باشد، `data.offers` شامل پیشنهاد آزمایشی است. در غیر این صورت `{"offers":[]}` برمی‌گردد. دورهٔ اشتراک در صلاحیت این پیشنهاد نقشی ندارد.

```json
{
  "offers": [{
    "id": "demo_campaign",
    "type": "discount",
    "title": "جشنوارهٔ آزمایشی",
    "line": "این جشنواره صرفاً آزمایشی است و برای خرید اعتبار ندارد؛ هیچ تخفیفی اعمال نمی‌شود.",
    "expiresAt": null
  }]
}
```

این endpoint بی‌حافظه است: با تکرار درخواست و `discountAlreadyShown=false` دوباره همان پیشنهاد را می‌دهد. جلوگیری از نمایش تکراری فعلاً مسئولیت مصرف‌کننده است. null بودن انقضای نمونه، اعتبار تجاری ایجاد نمی‌کند. شرایط فوق قواعد کمپین واقعی نیستند.

## خطاهای موجود و محدودیت یکدستی

| HTTP | وضعیت | بدنه |
| --- | --- | --- |
| 401 | توکن نادرست یا غایب، با ورودی معتبر | `{"detail":"Unauthorized"}` |
| 422 | پارامتر/بدنهٔ نامعتبر یا فیلد اجباری غایب | `detail` به شکل آرایهٔ خطاهای FastAPI/Pydantic |
| 404 | مسیر ناموجود، از جمله مسیرهای پیش‌نویس فعلی | `{"detail":"Not Found"}` |
| 405 | روش نامعتبر برای مسیر موجود | `{"detail":"Method Not Allowed"}` |

نمونهٔ درخواست نامعتبر: همان بدنهٔ پیشنهاد با `planMonths=5` باید 422 بدهد. هر خطای اعتبارسنجی دارای محل فیلد، نوع خطا و پیام است؛ متن دقیق پیام و فیلدهای اضافی به نسخهٔ وابستگی‌ها وابسته‌اند و قرارداد پایدار نیستند. در درخواست هم‌زمان نامعتبر و بدون توکن، اعتبارسنجی می‌تواند پیش از کنترل توکن 422 بدهد؛ اولویت 401 تضمین نشده است.

خطاهای فعلی پوشش `ok/data/simulation/notice` ندارند. قطع اتصال و timeout اصولاً پاسخ HTTP تضمین‌شده ندارند. آداپتور فعلی خطای خواندن یا پوشش نامعتبر را به `GatewayUnavailable` تبدیل می‌کند. بدنهٔ خطای خام upstream نباید مستقیماً به کاربر داده شود.

## هدف پیش‌نویس در مرحلهٔ بعد: هنوز پیاده‌نشده

این قسمت تصمیم محلی پیشنهادی برای پیاده‌سازی مرحلهٔ سوم است و تضمین سرویس رسمی نیست. در این مرحله هیچ endpoint نوشتنی فعال نمی‌شود.

نمونهٔ منسجم ساخت، وضعیت draft/expired و خطاهای 409/410/404/422 در [نمونه‌های هدف پیش‌نویس](examples/launcho-draft-target-v1.json) ثبت شده‌اند. برچسب proposed-not-implemented و ساعت مرجع ثابت آن‌ها را از پاسخ اجرایی امروز جدا می‌کند. تست، ورودی و مبلغ ساخت و پذیرش خروجی توسط هسته را در همان ساعت مرجع بررسی می‌کند؛ این نمونه‌ها نتیجهٔ اجرای endpoint پیاده‌نشده نیستند.

### ساخت

`POST /signup-drafts` با همان هدر آزمایشی و هدر اجباری `Idempotency-Key`. کلید رشتهٔ غیرخالی ASCII با طول 16 تا 128 از حروف، اعداد، خط تیره و زیرخط باشد؛ مقدار محرمانه یا دادهٔ شخصی در آن نباشد.

```json
{
  "kind": "shop",
  "businessName": "فروشگاه آزمایشی",
  "category": "test-category",
  "planMonths": 3,
  "template": "test-template",
  "domain": {"label": "example", "tld": "ir"}
}
```

نام کسب‌وکار، صنف، دوره، قالب و domain اجباری‌اند؛ kind پیش‌فرض shop دارد و همیشه در درخواست نرمال‌شده ارسال می‌شود. نام کسب‌وکار پس از حذف فاصلهٔ ابتدا/انتها 1 تا 80 کاراکتر، شناسهٔ صنف و قالب 1 تا 100 کاراکتر و دوره دقیقاً عدد صحیح 3، 6 یا 12 است. شناسه‌ها باید در کاتالوگ آزمایشی جداگانه معتبر باشند؛ شناسه‌های این مثال در کاتالوگ فعلی موجود نیستند و اکنون درخواست موفق ایجاد نمی‌کنند. فیلد اضافی، موبایل، رمز، OTP، روش پرداخت و مبلغ ورودی رد شوند.

هستهٔ اصلی در `ConversationCore.complete` دامنه را اجباری می‌داند و بدون آن مرور را با 422 متوقف می‌کند. ساختار دامنه مطابق `DomainChoice` در `app/models/schemas.py` است: یا `{"ownDomain":"example.ir"}` یا `{"label":"example","tld":"ir"}`، بدون ترکیب دو شکل. قرارداد با همین رفتار موجود هماهنگ است. حذف الزام دامنه از هسته تصمیم جداگانه‌ای است؛ در این بخش هسته و ویجت تغییر نمی‌کنند و جریان رابط فاقد دامنه کامل معرفی نمی‌شود.

پاسخ هدف ساخت و replay هر دو HTTP 200 با پوشش مشترک و data زیر است. تمام فیلدها اجباری و زمان‌ها ISO 8601 دارای منطقهٔ زمانی UTC هستند:

```json
{
  "ref": "sd_local_example01",
  "status": "draft",
  "createdAt": "2026-11-12T12:00:00Z",
  "expiresAt": "2026-11-13T12:00:00Z",
  "confirmUrl": "https://launcho.ir/start?signup=sd_local_example01",
  "quote": {"total": 17400000, "isFinal": false}
}
```

این پاسخ فقط fixture آزمون اعتبارسنجی هسته است؛ لینک آن صادرشده از لانچو نیست و نباید باز یا به مشتری تحویل داده شود. برای نمونهٔ shop، دورهٔ 3 و دامنهٔ جدید ir، total برابر 15000000 + 2400000 + 0 = 17400000 تومان نمونه است. برای ownDomain هزینهٔ اتصال در fixture مشخص نشده است؛ مبلغ تازه حدس زده نشود. اتصال واقعی باید confirmUrl را از پاسخ معتبر upstream بگیرد و هرگز خودش آن را نسازد. هیچ مسیر preview یا لینک محلی جدید تعریف نمی‌شود. mock پرداخت، تأیید موبایل، فعال‌سازی و انتشار انجام نمی‌دهد.

### تکرار، تعارض، انقضا و ماندگاری هدف

- کلید یکسان و payload معتبر یکسان: همان ref و همان نتیجهٔ ذخیره‌شده؛ پیش‌نویس و زمان انقضای تازه نسازد.
- نرمال‌سازی مطابق `normalize_draft` در `app/services/launcho_contract.py`: فیلد اضافه و null برای فیلد اجباری رد می‌شود؛ فاصلهٔ ابتدا و انتهای رشته‌ها حذف، kind غایب برابر shop و جایگزین‌های null در domain حذف می‌شوند. بزرگی/کوچکی حروف دامنه و شناسه‌ها حفظ می‌شود. ترتیب کلیدهای شیء مهم نیست؛ JSON نرمال‌شده با کلید مرتب مبنای مقایسه است. دامنهٔ کلید تمام عملیات ساخت این mock است، نه یک جلسهٔ مرورگر.
- ترتیب هدف: احراز هویت و اعتبارسنجی شکلی کلید و payload، جست‌وجوی کلید، مقایسه و replay/تعارض/انقضا؛ فقط برای کلید جدید، بررسی موجودی کاتالوگ و ایجاد انجام شود. حذف بعدی قالب نباید replay ثبت‌شده را خراب کند. payload از نظر شکلی نامعتبر با کلید قبلی 422 است؛ payload متفاوت معتبر با کلید منقضی تا پیش از پاکسازی 409 است.
- کلید یکسان با payload متفاوت: 409 `idempotency_conflict`، بدون نوشتن جدید.
- ذخیرهٔ کلید، اثر عملیات و نتیجه در یک تراکنش پایدار انجام شود؛ هم‌زمانی، restart و timeout بعد از ثبت باعث تکرار ساخت نشود.
- زمان اعتبار و نگهداری در مرحلهٔ پیاده‌سازی تنظیم‌پذیر باشند: `draft_ttl_seconds` و `idempotency_retention_seconds` عدد صحیح مثبت و retention حداقل برابر TTL باشد. 86400 و 604800 فقط ورودی fixture آزمون‌اند تا فاصلهٔ انقضا تا پایان replay آزمایش شود؛ پیش‌فرض استقرار یا سیاست مصوب نیستند. در now >= expiresAt پیش‌نویس منقضی و در now >= retainUntil رکورد قابل پاکسازی است. زمان‌ها از ایجاد اولیه محاسبه شوند و retry آن‌ها را تمدید نکند.
- replay همان payload پس از انقضا، طی مهلت نگهداری: 410 `draft_expired`؛ کلید متفاوت در این مرحله عملیات جدید محسوب می‌شود.
- پس از retainUntil، تضمین replay برای کلید حذف‌شده وجود ندارد؛ مصرف‌کننده نباید بعد از مهلت قراردادی کلید قدیمی را retry کند. پاکسازی بعد از مهلت مستند و قابل‌آزمون باشد.
- ذخیرهٔ پایدار mock جدا از دیتابیس جلسه باشد. دادهٔ آزمون ایزوله شود؛ SQLite روی دیسک محلی برای یک سرویس کافی است، تضمین چند نمونه نمی‌دهد.

### خواندن وضعیت هدف

`GET /signup-drafts/{ref}` با احراز هویت؛ ref مطابق `sd_[A-Za-z0-9_-]{4,128}`. وضعیت‌های قابل تولید این mock فقط `draft` و `expired` هستند. پاسخ خواندن HTTP 200 با پوشش مشترک، ref، status، createdAt و expiresAt؛ در انقضا `status=expired` برگردد. شناسهٔ ناشناخته 404 و شکل نامعتبر 422 است. سایر وضعیت‌های پذیرفته‌شده در هسته، مانند paid، مجوز شبیه‌سازی موفقیت پرداخت نیستند.

### خطای یکدست هدف برای مسیرهای جدید

```json
{
  "ok": false,
  "error": {"code": "idempotency_conflict", "message": "این کلید قبلاً برای اطلاعات دیگری استفاده شده است."},
  "simulation": true,
  "notice": "این پاسخ متعلق به محیط آزمایشی است."
}
```

| HTTP | code هدف | اثر |
| --- | --- | --- |
| 401 | unauthorized | عدم پذیرش عملیات |
| 422 | invalid_request / invalid_idempotency_key / invalid_option | عدم پذیرش عملیات |
| 404 | draft_not_found | خواندن شناسهٔ ناموجود |
| 409 | idempotency_conflict | عدم ایجاد عملیات جدید؛ عملیات قبلی ممکن است موجود باشد |
| 410 | draft_expired | پیش‌نویس قبلی وجود داشته و منقضی است |
| 503 | service_unavailable | پیش از ثبت، اگر عدم انجام عملیات قطعی باشد |

در قطع اتصال یا خطای نامطمئن پس از ارسال، مصرف‌کننده نتیجه را نامعلوم بداند و فقط همان کلید و payload را تکرار کند. HTTP 5xx به‌تنهایی اثبات انجام‌نشدن عملیات نیست. خطای تعارض هم اثبات نبود عملیات قبلی نیست. شکل خطاهای مسیرهای موجود در این مرحله تغییر نمی‌کند؛ یکدست‌کردن آن‌ها نیازمند تغییر نسخه و تطبیق تست/مصرف‌کننده است.

## شکاف اتصال و وابستگی‌ها

1. `LocalMockGateway` فعلاً `can_create=False` دارد؛ افزودن endpoint به‌تنهایی مسیر تأیید را فعال نمی‌کند.
2. قرارداد مستقیماً با `ConversationCore.validate_result` هماهنگ است: ref با الگوی سند، status=draft، انقضای آینده با timezone، total عدد صحیح نامنفی، isFinal دقیقاً false و لینک `https://launcho.ir/start?signup={ref}` بدون fragment یا پارامتر اضافه. لینک واقعی فقط از upstream دریافت شود. تست اتصال، مسیرهای HTTP اصلی جلسه/ویرایش/مرور/تأیید/وضعیت را با LaunchoDraftGateway واقعی و پاسخ upstream جایگزین‌شده اجرا می‌کند؛ هسته، routeها و اعتبارسنجی لینک تغییر نمی‌کنند.
3. کاتالوگ فعلی خالی است؛ تست مثبت ساخت نیازمند fixture آزمایشی جدا با برچسب مشخص است، بدون معرفی آن به‌عنوان کاتالوگ واقعی.
4. آداپتور ساخت، 409 را نتیجهٔ نامعلوم نگه می‌دارد: تعارض ممکن است به عملیات قبلی مربوط باشد و مجوز ساخت با کلید تازه نیست. تست، حفظ همان کلید در retry را بررسی می‌کند. معنای قطعی کدهای upstream باید با قرارداد رسمی تطبیق داده شود. کش قیمت/گزینه 600 ثانیه و اطلاعات سرویس 60 ثانیه است؛ این‌ها تنظیمات محلی‌اند و SLA رسمی نیستند.
5. قرارداد رسمی، schema نهایی کاتالوگ، زمان نگهداری، آدرس‌های مجاز و دسترسی sandbox هنوز وابستگی اتصال واقعی‌اند. صفحات عمومی سایت جای قرارداد API را نمی‌گیرند.

## پذیرش مرحلهٔ قرارداد

- مسیرهای موجود و هدف جدا و نسخهٔ محلی مشخص‌اند.
- نمونه‌های کامل داده، درخواست موفق، نبود پیشنهاد، نبود کاتالوگ و خطاهای پایدار همراه سند هستند.
- قواعد پیش‌نویس برای تکرار، تعارض، هم‌زمانی، انقضا و restart قابل تبدیل به تست‌اند.
- اختلاف با هسته بدون تغییر آن ثبت شده است؛ اتصال واقعی یا ساخت محلی فعال معرفی نشده است.
- آزمون پذیرش: `python -m unittest discover -s tests -p test_launcho_contract.py -v`. این آزمون، پاسخ‌های واقعی TestClient و مسیر اصلی هسته تا آداپتور را بررسی می‌کند؛ مدل و شبکهٔ واقعی فراخوانی نمی‌شوند.

## ساختار ماشینی و اثر بر هم‌تیمی‌ها

ساختار درخواست از [schema تولیدشده](examples/launcho-draft-request.schema.json) و مدل `DraftRequest` قابل خواندن است؛ مسیرهای موجود نیز OpenAPI خود FastAPI را دارند. تولید مجدد schema و نمونه‌ها با `python tests/export_launcho_contract.py` انجام می‌شود. schema مجموعهٔ نوع‌ها را تعریف می‌کند؛ قواعد متقابل domain و رد float/bool/string برای planMonths در `normalize_draft` اجرا و تست می‌شوند. اعتبار شناسهٔ کاتالوگ نیازمند داده است و از schema به‌تنهایی نتیجه نمی‌شود.

ساختار پاسخ‌های مهم:

| پاسخ | الزامات و null |
| --- | --- |
| service-info | contactUrl و overview رشته؛ useCases و featureSummary آرایهٔ رشته؛ در fixture فعلی همه موجود و غیرnull |
| ساخت برای هسته | ref، confirmUrl، status و expiresAt رشتهٔ اجباری؛ quote شیء اجباری با total صحیح نامنفی و isFinal دقیقاً false؛ هیچ‌کدام null نیستند |
| ذخیرهٔ mock هدف | createdAt رشتهٔ UTC اجباری افزوده بر پاسخ هسته؛ هسته آن را ذخیره نمی‌کند |
| خواندن وضعیت برای هسته | ref و status اجباری؛ وضعیت‌های مجاز draft/opened/mobile_verified/invoiced/paid/active/expired |
| خواندن mock هدف | فقط draft یا expired؛ createdAt و expiresAt نیز اجباری؛ null نیستند |
| پیشنهاد | offers آرایه؛ هر نمونه id، type، title و line رشته و expiresAt رشتهٔ زمان یا null |

فیلد اضافی در پاسخ ممکن است وجود داشته باشد؛ هسته فقط فیلدهای لازم را ذخیره می‌کند. آرایهٔ خالی به معنی نبود گزینه است، نه قیمت صفر یا اجازهٔ ساخت گزینهٔ فرضی.

اثر عملی تغییرات نسخهٔ ۱٫۱:

- نفر اول: هسته و routeها دست‌نخورده‌اند؛ الزام domain همان الزام موجود است. خطای 409 همچنان نتیجهٔ نامعلوم است. تغییر نوع دامنه یا حذف الزام آن تصمیم جداگانه است.
- نفر ویجت: جریان بدون domain هنوز با هستهٔ فعلی کامل نمی‌شود. این بخش هیچ مسیر یا لینک محلی جایگزین و هیچ endpoint تازه‌ای برای ویجت معرفی نمی‌کند.
- نفر اتصال: آداپتور، ورودی نامعتبر و کلید خارج از الگو را پیش از شبکه با GatewayRejected(422, code) رد می‌کند؛ kind پیش‌فرض و حذف nullهای domain خروجی نرمال‌شده را تعیین می‌کنند. کلید معتبر هسته بدون تغییر عبور می‌کند. نمونهٔ لینک رسمی فقط برای آزمون است؛ لینک عملیاتی باید از upstream معتبر صادر شده باشد.

تطبیق با هسته توسط آزمون قابل اثبات است؛ این سند ادعای تأیید انسانی هم‌تیمی‌ها یا قرارداد رسمی لانچو ندارد. نسخهٔ ۱٫۱ اصلاح سند اولیه و افزودن اعتبارسنجی آداپتور است؛ مصرف‌کنندهٔ مستقیم آداپتور که قبلاً payload ناقص یا کلید کوتاه می‌فرستاده باید اصلاح شود. هیچ API جدیدی فعال نشده است.

## نتیجهٔ بررسی این نسخه

در ۲۰۲۶-۱۱-۱۲، با Python 3.12.16 در محیط موقت مستقل، `python -m unittest discover -s tests -v` اجرا شد: هر 90 آزمون موفق، شامل 10 آزمون فایل جدید قرارداد. 19 نمونهٔ HTTP موجود با TestClient تطبیق داده شدند؛ مثال هدف پیش‌نویس نیز با اعتبارسنجی هسته و محاسبهٔ fixture بررسی شد. `git diff --check` بدون خطا بود.

Python محیط قبلی 3.9.6 است و برای annotationهای فعلی پروژه کافی نیست؛ برای این بررسی محیط اصلی یا فایل .env تغییر نکرد. وابستگی‌ها از requirements بدون قفل نسخه نصب شدند؛ این نتیجه تضمین یکسان‌بودن تمام محیط‌های دیگر نیست. هیچ درخواست واقعی به مدل یا API لانچو، هیچ ساخت پیش‌نویس واقعی و هیچ انتشار یا PR انجام نشده است. ساخت و ذخیرهٔ پایدار پیش‌نویس در خود mock همچنان مرحلهٔ بعد است.

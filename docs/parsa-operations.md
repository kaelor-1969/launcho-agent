# تحویل بک‌اند پارسا — ۱۳ نوامبر ۲۰۲۶

## مبنا و مالکیت

کپی اصلی C در آغاز بررسی تمیز و روی 5c691e7 بود. مسیر ریشه D مخزن نیست؛ تغییرات در local-review انجام شدند. اصلاحات قبلی کاتالوگ، پاسخ و ویجت بازبینی و در مبنای مشترک 694c4b9 ثبت شدند؛ برای آن بخش‌ها کدنویسی جدید انجام نشد. سه شاخه work/parsa-backend، work/mock-integration و work/widget از همین مبنا ساخته شدند. origin همچنان مسیر محلی C است؛ برای انتشار به آن push نکنید. تغییرات جدید بک‌اند در work/parsa-backend قرار دارند.

## اجرای مستقل بدون کلید

از ریشه همین مخزن، Python 3.11 یا جدیدتر:

```text
python -m venv .venv
python -m pip install -r requirements-dev.txt
python tests/check_demo.py --agent-port 8010 --mock-port 8011 --serve
```

پس از ایجاد محیط، python را با `.venv\Scripts\python.exe` در ویندوز و `.venv/bin/python` در مک جایگزین کنید. اسکریپت برای هر اجرا دو دیتابیس موقت مستقل می‌سازد، تنظیمات مدل و API واقعی را خنثی می‌کند و به stdin وابسته نیست. Ctrl+C هر دو سرویس را می‌بندد. پورت اشغال‌شده با پیام روشن رد می‌شود؛ پردازش دیگری متوقف نمی‌شود. برای اجرای HTTP اختصاصی، `python tests/check_backend_http.py --url http://127.0.0.1:8010` را در ترمینال دوم اجرا کنید. اسکریپت قدیمی check_local_http.py به مسیر دیتابیس ثابت وابسته است و برای دیتابیس موقت launcher مناسب نیست.

در اجرای دستی پایدار، LAUNCHO_SESSION_DB را به فایل اختصاصی هر توسعه‌دهنده و LAUNCHO_MOCK_DRAFT_DB را به فایل مجزای mock تنظیم کنید. اسرار را از shell یا فایل خصوصی تأمین کنید و در خروجی قرار ندهید.

## سیاست اجرا

- LAUNCHO_ENV=production، استفاده از mock را رد می‌کند و مسیر مطلق LAUNCHO_SESSION_DB و LAUNCHO_FRAME_ANCESTORS صریح می‌خواهد.
- LAUNCHO_FRAME_ANCESTORS فهرست originهای میزبان مجاز iframe با کاماست؛ شامل scheme و port لازم، بدون path یا wildcard. این سیاست CSP فقط اجازه جاسازی را کنترل می‌کند؛ محدودسازی script-src نیازمند هماهنگی مالک ویجت و حذف inlineهای فعلی است.
- LAUNCHO_CORS_ORIGINS فهرست صریح originهای مجاز API است. مقدار خالی در production اجازه cross-origin نمی‌دهد. ویجت داخل iframe هم‌مبدأ API است؛ origin صفحه میزبان فقط در صورت نیاز واقعی به فراخوانی مستقیم API مجاز شود. توسعه به‌طور پیش‌فرض CORS باز دارد.
- LAUNCHO_REQUESTS_PER_MINUTE پیش‌فرض ۱۲۰ درخواست API برای هر IP اتصال در هر پردازش است؛ forwarding headers خوانده نمی‌شوند. پشت proxy باید رفتار IP واقعی آزموده و محدودیت عمومی در edge نیز اعمال شود. این سقف تضمین بودجه مالی مدل نیست؛ سقف هزینه باید در حساب ارائه‌دهنده نیز تنظیم شود. تغییر پارامترهای مدل در مالکیت نفر دوم است.
- LAUNCHO_MAX_BODY_BYTES پیش‌فرض ۳۲۷۶۸ بایت است؛ بدنه بزرگ‌تر با 413 رد می‌شود. 429 دارای Retry-After است. جزئیات داخلی خطا، پیام مدل و توکن در لاگ جدید چاپ نمی‌شوند. API دارای Cache-Control: no-store است.
- فقط یک نمونه و یک worker با دیسک پایدار اجرا شود. محدودکننده نرخ حافظه‌ای است و پس از restart بازنشانی می‌شود؛ SQLite جایگزین ذخیره مشترک چند نمونه نیست.

## سلامت، نگهداری و بکاپ

`/health/live` فقط زنده‌بودن پردازش را می‌سنجد. `/health/ready` دسترسی تراکنشی SQLite و دسترسی قراردادی به گزینه‌ها و قیمت را بررسی می‌کند؛ شکست آن 503 عمومی است. این مسیر فراخوانی نوشتنی، مدل یا پرداخت انجام نمی‌دهد و سلامت مدل یا صحت قرارداد رسمی را تضمین نمی‌کند. پایش بیرونی برای این دو مسیر، نرخ 5xx/429، فضای دیسک و خطای session_cleanup_failed تنظیم شود.

پاک‌سازی در startup و سپس هر پنج دقیقه اجرا می‌شود. انقضای جلسه بلافاصله در احراز هویت اعمال می‌شود؛ حذف فیزیکی تا نوبت بعدی طول می‌کشد. TTL پیش‌فرض ۲۴ ساعت است؛ LAUNCHO_SESSION_TTL_SECONDS بین ۶۰ و ۸۶۴۰۰ تنظیم می‌شود. حذف جلسه رکوردهای مرور و پیشنهاد وابسته را با cascade پاک می‌کند؛ secure_delete فعال است. حذف از بکاپ‌ها و لایه ذخیره میزبان جداگانه مدیریت شود. جلسه با نتیجه نامعلوم پس از TTL هم حذف می‌شود؛ بازیابی محدود به عمر قابلیت جلسه است.

```text
python scripts/session_admin.py check --db data/sessions.sqlite3
python scripts/session_admin.py cleanup --db data/sessions.sqlite3
python scripts/session_admin.py backup --db data/sessions.sqlite3 --file backups/sessions-2026-11-13.sqlite3
python scripts/session_admin.py restore --db data/restored.sqlite3 --file backups/sessions-2026-11-13.sqlite3
```

backup از SQLite online backup استفاده می‌کند؛ مقصد باید تازه باشد و integrity بررسی می‌شود. برای restore سرویس را متوقف کنید، در مسیر تازه بازیابی کنید و سپس LAUNCHO_SESSION_DB را تغییر دهید. فایل موجود بازنویسی نمی‌شود. بکاپ‌ها شامل داده جلسه و قابلیت‌های هش‌شده‌اند: خارج از Git، با دسترسی محدود و رمزگذاری دیسک نگهداری شوند. پیشنهاد عملیاتی اولیه: بکاپ روزانه با نگهداری هفت روز؛ تصویب سیاست نگهداری با مالک محصول باقی است. این ابزار فقط دیتابیس هسته را مدیریت می‌کند؛ بکاپ و پاک‌سازی mock با مالک نفر دوم است.

## استقرار و بازگشت

Docker با کاربر غیر root و healthcheck اجرا می‌شود. یک volume قابل نوشتن برای UID 10001 روی /app/data نصب کنید. render.yaml تک‌نمونه با دیسک /var/data، readiness و نوشتن واقعی غیرفعال تنظیم شده است. originهای میزبان و متغیرهای خصوصی باید در محیط مقصد تأمین شوند. فعال‌سازی LAUNCHO_ENABLE_DRAFTS فقط پس از تأیید قرارداد و آزمون آداپتور مجاز است. CI برای ویندوز، مک و لینوکس، تست‌ها و اجرای بدون کلید را تعریف می‌کند؛ job جدا Docker را می‌سازد.

برای rollout ابتدا بکاپ، شناسه image/commit قبلی و متغیرهای پیکربندی را ثبت کنید؛ نسخه تازه را با همان دیسک در staging اجرا و readiness و smoke HTTP را بررسی کنید. برای rollback نوشتن را متوقف و image قبلی را بازگردانید. این تغییر schema مهاجرت مخرب ندارد. اگر بازیابی داده لازم شد، سرویس را متوقف و backup را در مسیر تازه restore کنید؛ بازگشت داده ممکن است نتیجه عملیات upstream را محلی فراموش کند و پیش از فعال‌سازی نوشتن نیازمند تطبیق است. API واقعی در این تحویل فراخوانی نشده است.

## شواهد و محدودیت تحویل

- ۸۵ تست موجود پیش از تغییرات پاس شدند؛ ۹۰ تست پس از تغییرات، شامل بازیابی نتیجه نامعلوم پس از restart هسته، بکاپ و بازیابی واقعی، cascade، سیاست production، محدودیت بدنه/نرخ و readiness پاس شدند.
- تست JavaScript با --experimental-vm-modules پاس شد؛ آزمون مرورگر محسوب نمی‌شود.
- اجرای دو سرویس در ویندوز بدون کلید روی ۸۰۱۰/۸۰۱۱ و ۸۰۰۰/۸۰۰۱ موفق بود. smoke HTTP جدید برای فروشگاه و سایت‌ساز، مالکیت، revision قدیمی، نبود ساخت پیش از تأیید، هم‌زمانی، replay، preview، وضعیت و readiness پاس شد.
- Docker و gh در PATH این محیط موجود نیستند؛ build کانتینر، اجرای CI، اجرای واقعی مک، انتشار GitHub/PR و استقرار خارجی انجام نشده‌اند. قرارداد رسمی، محیط آزمون، مقصد و دسترسی استقرار بیرونی هنوز لازم‌اند. فایل پیکربندی و تعریف CI معادل اجرای موفق آن‌ها نیست.
- دسترسی خواندنی GitHub با backend=openssl موفق بود و HEAD برابر f1d61fe تأیید شد. تلاش انتشار اتمی چهار شاخه به URL صریح GitHub به علت نبود اعتبارنامه و خطای wincredman شکست خورد؛ هیچ شاخه‌ای منتشر نشد. origin تغییر نکرد. متن آماده PR در parsa-pr.md است. برای انتشار، اعتبارنامه GitHub یا اتصال دارای مجوز نوشتن لازم است؛ از force push استفاده نشده است.
- توکن iframe پس از refresh، تجربه مرورگر، نصب میزبان و تطبیق بصری متعلق به نفر سوم باقی می‌مانند. یافته‌های خارج از محدوده: اسکریپت قدیمی HTTP به مسیر ثابت DB وابسته است؛ سقف توکن/هزینه مدل باید با نفر دوم و تنظیمات ارائه‌دهنده تکمیل شود.

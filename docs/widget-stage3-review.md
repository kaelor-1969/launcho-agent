# گزارش مرحلهٔ ۳: پاسخ‌ها و بازیابی از خطا

تاریخ: ۲۰۲۶-۱۱-۰۸

## نتیجه

۲۲ سناریوی مرورگر پاس شد: ۱۱ حالت در دسکتاپ ۱۲۸۰×۹۰۰ و همان ۱۱ حالت در موبایل شبیه‌سازی‌شدهٔ ۳۹۰×۸۴۴. تست‌ها در Chrome با Playwright و روی فایل‌های اصلی frontend اجرا شدند. در این مرحله تغییر تازه‌ای در کد اجرایی ویجت لازم نبود؛ فایل آزمون و این گزارش اضافه شدند.

## رفتار بررسی‌شده

- تا قبل از دریافت نتیجه، نشانگر انتظار دیده می‌شود و ارسال غیرفعال است.
- پاسخ موفق در گفتگو نمایش داده می‌شود؛ انتظار متوقف و امکان ارسال پیام بعدی فراهم می‌شود.
- خطای سرور، شبکه و پاسخ نامعتبر پیام فارسی مناسب و دکمهٔ «تلاش مجدد» دارند؛ پاسخ نامعتبر حباب دستیار نمی‌سازد.
- پس از خطا، تلاش برای ارسال پیام تازه باعث درخواست یا حباب تازه نمی‌شود؛ ابتدا باید پیام شکست‌خورده دوباره ارسال شود.
- تلاش مجدد همان متن قبلی را ارسال می‌کند و حباب کاربر را تکرار نمی‌کند.
- در زمان تلاش مجدد، تحریک ۱۰ بارهٔ retry، submit و Enter درخواست اضافه ایجاد نمی‌کند.
- بعد از بازیابی، خطا و انتظار مخفی می‌شوند، پیش‌نویس پیام بعدی حفظ می‌شود و قابل ارسال است.
- در پایان هر حالت خطا، دقیقاً سه درخواست وجود دارد: ارسال اولیه، retry و پیام بعدی. در حالت موفق، دقیقاً دو درخواست وجود دارد.
- هیچ خطای JavaScript ثبت نشد. خطاهای مورد انتظار شبکه/HTTP بخشی از mock هستند.

## نحوهٔ اجرا و شواهد

با frontend در دسترس روی سرور محلی و Playwright و Chrome نصب‌شده:

```powershell
python tests/widget_responses_browser.py --base-url http://127.0.0.1:8000
```

فقط در context مجزای مرورگر آزمون، HTML صفحهٔ `/widget/demo.html` رهگیری و `data-demo` غیرفعال می‌شود تا مسیر واقعی `sendMessage` فراخوانی شود. همهٔ درخواست‌های API همان صفحه توسط Playwright رهگیری و پاسخ داده یا قطع می‌شوند. فایل اصلی demo تغییر نمی‌کند و هیچ درخواست AI واقعی ارسال نمی‌شود.

خروجی در `artifacts/widget-stage3/` است:

- `report.json`: نتیجهٔ هر ۲۲ حالت، تعداد درخواست‌ها و پیام‌ها.
- ۱۴ تصویر: پاسخ موفق و حالت خطا/بازیابی برای خطای ۵۰۰، شبکه و JSON خراب در هر دو اندازه.
- تصاویر خطای سرور و شبکه و بازیابی در موبایل و خطای سرور و بازیابی در دسکتاپ بازبینی بصری شدند.

پوشهٔ artifacts در گیت نادیده گرفته می‌شود؛ برای تحویل PR تصاویر باید ضمیمه شوند.

## محدودیت‌ها و باقی‌مانده‌ها

- این بررسی روی frontend با سرور محلی فایل‌ها و API شبیه‌سازی‌شده انجام شد؛ اجرای FastAPI و سرویس واقعی را تأیید نمی‌کند.
- قطع شبکه با abort مرورگر شبیه‌سازی شد؛ اتصال فیزیکی دستگاه قطع نشد.
- گوشی واقعی، صفحه‌کلید واقعی، Safari و انتظار کامل ۴۵ ثانیه‌ای timeout در این مرحله بررسی نشدند.
- اگر بک‌اند خطای داخلی را با HTTP 200 و یک `reply` متنی معتبر برگرداند، فرانت‌اند آن را پاسخ عادی تشخیص می‌دهد. تفکیک آن نیازمند قرارداد خطای مشخص بک‌اند است.
- بررسی اجرای HTML و اسکریپت در متن پاسخ، مربوط به مرحلهٔ ۴ است.

# جلوگیری از پیشنهاد مالی فرضی و تقویت پاسخ‌های دستیار

## متن آمادهٔ PR

عنوان پیشنهادی: Add persistent mock drafts, validated catalogs and financial offer contracts

درخواست پیشنهاد پیش‌تر اعتراض قیمت، نیاز به پیش‌پرداخت کمتر و مرحلهٔ ثبت‌نام را با مقادیر ثابت ارسال می‌کرد. اکنون آداپتور از متن و تاریخچهٔ کاربر زمینهٔ مالی می‌سازد و بدون مرحله و زمینهٔ معتبر، پیشنهاد درخواست نمی‌کند. فراخوانی‌های قدیمی هسته همچنان سازگارند اما فهرست پیشنهاد خالی می‌گیرند؛ راهنمای تعرفه و اقساط فعال می‌ماند.

پاسخ‌های مدل برای نمونه‌های ادعای ساخت/پرداخت، موجودی، تضمین فروش، مبلغ حروفی و لینک‌های تأییدنشده کنترل می‌شوند. انتخاب‌های ابزار پیش از بازگشت با مدل Preferences موجود بررسی می‌شوند تا دادهٔ حساس وارد انتخاب‌ها نشود. متن‌های راهنمای فرم و پشتیبانی طبق بازخورد کاربر اصلاح شده‌اند؛ لینک دقیق سایت‌ساز پس از بررسی دستی کاربر مجاز است.

### اعتبارسنجی

- اجرای کامل unittest: هر ۱۴۷ تست موفق با Python 3.11.18؛ ۲۹ تست جدید نسبت به مبنای ۱۱۸ تست (۷ مالی، ۱۲ ایمنی پاسخ و ۱۰ قرارداد پیشنهاد).
- تست‌ها شامل تغییر نظر/رد پیشنهاد، قطع سرویس، خروجی خراب ابزار، لینک نامعتبر، حفظ preferences و revision و ادامهٔ جلسه پس از timeout هستند.
- `git diff --check`: موفق.
- تست‌ها کنترل‌شده‌اند؛ تماس واقعی با مدل یا عملیات لانچو انجام نشده است.

### اثر و موارد باز برای بازبینی

- تا ارسال message/history/step/offer_state توسط مالک هسته، پیشنهاد خودکار در مسیر موجود خاموش است؛ این تغییر رفتار باید هنگام ادغام بررسی شود.
- نمایش checkoutOffer رشته‌ای فاقد مدرک غیرفعال است؛ قرارداد داخلی ساختاریافته آماده است اما اتصال نمایش در هسته و mapper رسمی لانچو باقی است.
- آداپتور وضعیت پایدار را صریح می‌گیرد؛ ذخیرهٔ شناسه و وضعیت پیشنهاد در هسته و اتصال آن هنوز با پارساست.
- فیلترهای الگو محور تضمین عمومی صحت پاسخ یا مقاومت مدل زنده نیستند و ممکن است برخی پاسخ‌های درست را هم محدود کنند.
- دریافت قرارداد رسمی، کاتالوگ واقعی، ارزیابی مدل زنده و پذیرش مشترک باقی است.
- در تغییرات مرحله‌های ۵ و ۶، هسته، schemaهای مشترک جلسه، routeها، frontend و دادهٔ کاتالوگ ویرایش نشده‌اند؛ PR کامل شامل commit قبلی mock و کاتالوگ هم هست. فقط تست پایتونی مرتبط با متن پاسخ در test_conversation_core هماهنگ شده است.

مرحله‌های guidance، collecting_preferences، review_ready، awaiting_confirmation و draft_created جای step عددی را در قرارداد جاری mock گرفته‌اند. خروجی canonical، state صریح هسته و schemaهای ماشینی اضافه شده‌اند. نمونه‌های HTTP نسخهٔ ۳ مرجع جاری پیشنهادها هستند؛ نسخهٔ ۲ سابقه است.

## تحویل به پارسا — متن آماده

«قرارداد داخلی internal-offers-v1 در docs/financial-offers-stage5.md آماده است. هر دو تابع message، history، step نام‌دار و offer_state می‌گیرند. پیام جاری جدا از تاریخچه است. {} فقط برای state احرازشدهٔ تازه مجاز است؛ نبود state درخواست پیشنهاد ایجاد نمی‌کند. فعلاً پس از هر نمایش مالی، کل جلسه برای پیشنهاد خودکار بعدی بسته می‌شود؛ تغییر این سیاست منتظر تصمیم محصول است. خروجی canonical با schema و نمونهٔ mock v3 آماده است؛ checkoutOffer رشته‌ای همچنان نمایش داده نمی‌شود. ثبت نمایش اتمیک، جداسازی جلسه و تست restart/retry/concurrency در مالکیت توست. برای اعمال بسته ابتدا git apply --check را اجرا کن؛ در صورت اختلاف مبنا، فایل‌های خودت را با نسخهٔ ما بازنویسی نکن.»

این پیام در این تحویل ارسال نشده است؛ کاربر می‌تواند آن را به پارسا بدهد.

## ترتیب ادامه و مسئول هر کار

1. کاربر: دریافت قرارداد API و مرجع تجاری رسمی از لانچو؛ اعلام وضعیت دسترسی مدل آزمایشی، بدون ارسال کلید در چت.
2. نفر دوم: تطبیق قرارداد رسمی با آداپتور/mock، تست قرارداد و ارزیابی مدل زنده پس از فراهم‌شدن محیط.
3. پارسا و نفر دوم: تعیین مرحله، ارسال زمینهٔ پیشنهاد، حفظ وضعیت پیشنهاد و تعیین مرز خروجی معتبر.
4. نفر سوم: اجرای مسیرهای رابط کاربری و خطا با خروجی نهایی؛ کنترل رندر لینک و عدم تأیید ناخواسته.
5. هر سه نفر: پذیرش مشترک shop/website، replay، تعارض، انقضا، نتیجهٔ نامعلوم و restart؛ هر مالک خطای بخش خود را رفع کند.
6. تحویل Git: بررسی diff کامل شاخه، commit فایل‌های متعلق به این بخش، push و ایجاد draft PR؛ پس از پذیرش مشترک آمادهٔ ادغام شود.

## وضعیت انتشار

انتشار این تحویل با درخواست صریح کاربر انجام می‌شود. PR به‌صورت Draft روی main آماده می‌شود؛ ادغام نهایی مشترک باقی است. ابزار gh موجود نیست و انتشار از طریق Git و API رسمی GitHub با اعتبارنامهٔ موجود انجام می‌شود. نتیجهٔ نهایی انتشار در پاسخ تحویل اعلام می‌شود.


## بررسی نهایی نسبت به main

در کپی جدا، پیش‌نمایش merge با main شش تعارض در mock_launcho.py، ai_service.py، draft_gateway.py، content/launcho-mock.json، docs/local-launcho-simulation.md و tests/test_mock_drafts.py نشان داد. main پیاده‌سازی متفاوت mock و کاتالوگ محلی دارد؛ انتخاب نسخه باید در ادغام مشترک انجام شود. نتیجهٔ ۱۴۷ تست برای شاخهٔ حاضر است؛ نتیجهٔ ادغام‌شده با main نیست.

فراخوانی قدیمی main با plan_months موقعیتی بدون TypeError پذیرفته می‌شود؛ مرحلهٔ عددی به صلاحیت فرضی تبدیل نشده و خروجی خالی است. fallback کلید محلی برای سازگاری راه‌اندازی بدون کلید حفظ شده است. گزارش اسناد پیشنهادی کارفرما در main بررسی شد؛ تعیین نسخهٔ مرجع و سرویس آماده همچنان وابستگی واقعی است.

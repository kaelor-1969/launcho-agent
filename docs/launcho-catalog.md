# کاتالوگ صنف و قالب؛ قرارداد، منابع و وضعیت تأیید

تاریخ بازبینی مخزن: ۲۰۲۶-۱۱-۱۲. نسخهٔ ساختار کاتالوگ `1.0.0` است. این سند و schema داخلی جای قرارداد رسمی لانچو نیستند. هیچ شناسهٔ واقعی قابل ثبت در دادهٔ تحویلی فعلی تأیید نشده است؛ کاتالوگ عادی همچنان صادقانه unavailable است.

## فهرست داده‌ها و ناسازگاری‌های رسیدگی‌شده

| محل | وضعیت پیشین و ناسازگاری | وضعیت تحویل |
| --- | --- | --- |
| `app/services/launcho_api.py` | صنف fashion با عنوان پوشاک و مد، قالب example-row با عنوان قالب نمونه و available=true؛ همان نمونه‌ها برای shop و website بدون سند سازگاری برمی‌گشتند | فهرست نمونه حذف شد؛ مسیر قدیمی اکنون همان کاتالوگ مستند unavailable را برمی‌گرداند و kind نامعتبر رد می‌شود |
| تابع قدیمی create_signup_draft | ref و لینک رسمی‌نما بدون هیچ عملیات upstream تولید می‌کرد | فراخوانی مستقیم با RuntimeError متوقف می‌شود؛ موفقیت و لینک ساختگی نمی‌دهد |
| `content/launcho-mock.json` | دو کاتالوگ خالی با هشدار، بدون schema و metadata سطح کاتالوگ | برای هر نوع خدمت، نسخه، منبع داخلی، تاریخ بازبینی و وضعیت pending اضافه شد؛ هیچ گزینه‌ای اختراع نشده است |
| `content/launcho-draft-test-catalog.json` | چهار گزینهٔ مصنوعی با metadata ناقص | دو صنف و دو قالب، جداگانه برای shop/website، با شناسه، منبع، تاریخ، وضعیت و سازگاری کامل test_only |
| `content/launcho-public.json` | نام و توضیح نمونه‌های عمومی مدا و دیجی‌کالا، بدون شناسهٔ رسمی ثبت‌نام | فقط مرجع آشنایی و مقایسه؛ به گزینهٔ قابل ثبت تبدیل نشده است |
| README و دارایی نمونهٔ الماس | تصویر و hook نمایشی، بدون شناسهٔ رسمی ثبت‌نام | صرفاً مرجع نمایشی؛ frontend و دارایی آن تغییر نکرده‌اند |
| آداپتور خواندن | پاسخ فاقد metadata را می‌پذیرفت؛ گزینه‌ها تا 600 ثانیه کش می‌شدند | ساختار و منبع بررسی می‌شوند؛ گزینهٔ test_only در live رد می‌شود؛ شناسه‌های قابل انتخاب تا تعریف قواعد رسمی revocation کش نمی‌شوند |

رجیستری ردیابی گزینه‌های قدیمی و مراجع عمومی در [فایل ممیزی](../content/launcho-catalog-audit.json) است. referenceIdهای public-mada/public-digikala/public-almas فقط کلید ممیزی‌اند و registrationId آن‌ها null است. این بررسی فهرست کامل ۲۳ قالب را دریافت یا تأیید نکرده است. اطلاعات عمومی موجود متعلق به سابقهٔ منابع مخزن است؛ تلاش دریافت صفحهٔ رسمی در این بررسی ناموفق بود و تأیید آنلاین تازه ادعا نمی‌شود.

## ساختار و قواعد مشترک

[schema ماشینی کاتالوگ](../content/launcho-catalog.schema.json) از مدل `SignupCatalog` در `app/services/catalog.py` تولید می‌شود. متد `selectable_catalog` تنها گزینه‌های مجاز را به مصرف‌کننده می‌دهد. قواعد ارتباطی نیز در همان مدل اعتبارسنجی می‌شوند و فقط از روی JSON Schema قابل استنتاج نیستند.

هر پاسخ کاتالوگ kind، catalogVersion، availability، notice، approvalStatus، source، reviewedAt، businessCategories و templates دارد. steps و templateCategories برای سازگاری نگه داشته شده‌اند و فعلاً خالی‌اند.

| فیلد هر گزینه | تعریف |
| --- | --- |
| id | رشتهٔ غیرخالی حداکثر 100 کاراکتر؛ در مجموعهٔ صنف یا قالب همان نوع خدمت یکتا |
| title | عنوان خوانا، 1 تا 120 کاراکتر |
| label | برای صنف اجباری، جهت سازگاری نام نمایشی موجود؛ قالب از title استفاده می‌کند |
| kind | دقیقاً shop یا website؛ باید با kind کاتالوگ یکی باشد |
| available | دقیقاً boolean؛ موجودی/دسترسی گزینه، مستقل از تأیید منبع |
| approvalStatus | یکی از test_only، pending، approved، inactive |
| source | شیء type و reference غیرخالی؛ ارجاع فایل داخلی یا منبع دقیق API/صفحه |
| reviewedAt | تاریخ معتبر YYYY-MM-DD برای بررسی همین رکورد؛ به معنی تضمین تازگی لحظه‌ای نیست |
| approvalEvidence | برای approved اجباری؛ ارجاع تأیید یا قرارداد مورد قبول مالک محصول؛ برای باقی وضعیت‌ها می‌تواند null باشد |
| compatibleCategoryIds | فقط قالب؛ آرایهٔ شناسه‌های صنف همان کاتالوگ یا null |

نوع source یکی از internal_fixture، official_api، official_page و unverified است. گزینهٔ approved برای ثبت، منبع official_api و approvalEvidence می‌خواهد؛ مشاهدهٔ قالب روی صفحهٔ عمومی به‌تنهایی تأیید قابل ثبت بودن آن نیست. این metadata ادعای تأیید را قابل ردیابی می‌کند؛ صحت سند تأیید باید توسط مالک محصول و با قرارداد رسمی بررسی شود، نه صرفاً با عوض‌کردن یک مقدار JSON.

## وضعیت‌ها و قابل‌انتخاب بودن

| وضعیت | معنا | رفتار انتخاب |
| --- | --- | --- |
| test_only — آزمایشی | دادهٔ ساختگی با منبع internal_fixture | فقط در پروفایل صریح test و mode محلی؛ هرگز live |
| pending — در انتظار تأیید | منبع، شناسه یا دسترسی هنوز تأیید نشده | available باید false باشد؛ از خروجی گزینه‌های قابل انتخاب حذف می‌شود |
| approved — تأییدشده | شناسه و منبع API با مدرک تأیید ثبت شده | فقط با available=true و سازگاری معتبر قابل انتخاب است |
| inactive — غیرفعال | گزینه حذف یا بازنشسته شده است | available باید false باشد؛ قابل انتخاب نیست |

available=false می‌تواند برای گزینهٔ approved هم استفاده شود؛ یعنی مدرک قبلی وجود دارد ولی گزینه اکنون قابل انتخاب نیست. وضعیت pending/inactive همراه با available=true دادهٔ ناسازگار است و کل کاتالوگ با خطای امن رد می‌شود.

در سطح کاتالوگ، availability=unavailable یعنی مجموعهٔ قابل استفاده نداریم؛ test_only یعنی فقط مجموعهٔ مصنوعی؛ available یعنی مجموعهٔ دارای گزینهٔ مجاز. انتخاب نیازمند مجازبودن هم سطح کاتالوگ و هم خود گزینه است. اگر صنف یا قالب قابل انتخاب باقی نماند، هر دو فهرست خروجی خالی و availability=unavailable می‌شود. دادهٔ خام برای ممیزی در content باقی می‌ماند؛ اطلاعات عمومی و pending به پاسخ قابل انتخاب نشت نمی‌کنند.

## سازگاری صنف و قالب

- kind قالب و صنف باید همان نوع خدمت کاتالوگ باشد؛ گزینهٔ website در shop رد می‌شود.
- compatibleCategoryIds=null یعنی محدودیت صنف در همان نوع خدمت تعریف نشده؛ به معنی سازگاری بین دو نوع خدمت نیست.
- آرایهٔ غیرخالی یعنی فقط صنف‌های فهرست‌شده مجازند. شناسهٔ ناموجود یا تکراری در این آرایه خطای ساختار است.
- آرایهٔ خالی یعنی هیچ صنفی مجاز نیست؛ قالبی با این مقدار نمی‌تواند available=true باشد.
- هنگام تولید خروجی، صنف‌های غیرفعال از سازگاری حذف می‌شوند؛ قالب بدون صنف مجاز باقی‌مانده نمایش داده نمی‌شود.
- mock هنگام ساخت جدید سازگاری انتخاب را دوباره بررسی می‌کند؛ ترکیب نامعتبر 422 incompatible_template می‌دهد.

نمونه‌های جداگانهٔ فعلی:

| نوع خدمت | صنف آزمایشی | قالب آزمایشی | سازگاری |
| --- | --- | --- | --- |
| shop | test-category | test-template | فقط test-category |
| website | test-website-category | test-website-template | فقط test-website-category |

هر چهار رکورد منبع `content/launcho-draft-test-catalog.json`، تاریخ 2026-11-12 و وضعیت test_only دارند. نام، شناسه و سازگاری آن‌ها صرفاً قرارداد آزمون است و دربارهٔ لانچوی واقعی چیزی ثابت نمی‌کند.

## نبود داده، خرابی سرویس و حذف گزینه

| وضعیت | رفتار |
| --- | --- |
| GET کاتالوگ موجود ولی هنوز تأییدنشده | HTTP 200، availability=unavailable، فهرست‌های خالی و توضیح فارسی |
| GET کاتالوگ دارای ساختار/منبع خراب در mock | HTTP 503، error.code=catalog_unavailable؛ دادهٔ نمونه جایگزین نمی‌شود |
| ساخت جدید بدون کاتالوگ قابل انتخاب | HTTP 503، catalog_unavailable؛ هیچ رکوردی ساخته نمی‌شود |
| شناسهٔ انتخاب‌شده ناموجود، در کاتالوگی که گزینه‌های معتبر دیگری دارد | HTTP 422، invalid_option |
| حذف آخرین قالب یا صنف قابل انتخاب | کاتالوگ unavailable می‌شود؛ ساخت تازه 503 می‌گیرد |
| قالب موجود ولی ناسازگار با صنف انتخابی | HTTP 422، incompatible_template |
| قطعی شبکه، 5xx یا پاسخ خراب API کاتالوگ در آداپتور | GatewayUnavailable؛ هستهٔ موجود آن را به خطای دسترسی گزینه‌ها تبدیل می‌کند؛ fallback به دادهٔ قدیمی نداریم |
| پاسخ آزمایشی در mode=live | GatewayUnavailable؛ دادهٔ مصنوعی واقعی معرفی نمی‌شود |
| حذف قالب بعد از ساخت پیش‌نویس موفق | replay همان کلید و بدنه تا پیش از انقضا همان نتیجهٔ ذخیره‌شده را می‌دهد؛ ساخت جدید به گزینهٔ حذف‌شده مجاز نیست |

فرق «فهرست خالی معتبر» و «سرویس قطع است» حفظ می‌شود. کاربر باید پیام متناسب بگیرد؛ قیمت، شناسه و قالب جایگزین حدس زده نمی‌شود. رفتار انقضا و نگهداری کلید همان [قرارداد پیش‌نویس](launcho-mock-contract-v2.md) است.

## اثر بر هم‌تیمی‌ها و وابستگی واقعی

هستهٔ جلسه، schemaهای مشترک و routeهای اصلی و frontend تغییر نکرده‌اند. نفر اول و نفر سوم باید بدانند که مسیر قدیمی دیگر fashion و example-row را پیشنهاد نمی‌کند و نبود کاتالوگ هنگام ساخت 503 است، نه شناسهٔ فرضی. fixtureهای واحد مستقل هم‌تیمی‌ها قرارداد API واقعی نیستند.

آداپتور live تا دریافت پاسخ دارای metadata قابل اعتبارسنجی، انتخاب‌ها را نمی‌پذیرد. اگر قرارداد رسمی شکل دیگری داشت، نفر دوم باید mapper آن را با منبع و مدرک واقعی پیاده کند؛ نباید metadata تأیید را از روی حدس پر کند. برای تکمیل اتصال، شناسه‌ها، موجودی فعلی، محدودیت سازگاری، مرجع تأیید و قواعد تغییر/حذف گزینه‌ها از لانچو لازم‌اند. تا آن زمان توسعه و تست با پروفایل مصنوعی جدا ادامه دارد.

## تولید و آزمون

```sh
python tests/export_launcho_contract.py
python -m unittest discover -s tests -p test_catalog.py -v
python -m unittest discover -s tests -v
```

تست‌ها metadata، schema، مسیر قدیمی، عدم ساخت لینک رسمی‌نما، وضعیت‌های چهارگانه، kind، شناسهٔ تکراری، سازگاری، حذف گزینه، replay پس از حذف، نبود کاتالوگ، پاسخ خراب و قطعی بدون fallback را بررسی می‌کنند. دادهٔ approved در تست transport کاملاً مصنوعی است و مدرک تأیید واقعی محسوب نمی‌شود.

نتیجهٔ تحویل در ۲۰۲۶-۱۱-۱۲ با Python 3.12.16: هر 118 آزمون پایتون موفق، شامل 9 آزمون جدید کاتالوگ. نمونه‌های HTTP و schema دوباره تولید و با اجرای API درون‌پردازه‌ای تطبیق داده شدند. `git diff --check` بدون خطا بود. هیچ تماس واقعی با مدل یا عملیات ثبت‌نام لانچو، هیچ استقرار، commit یا PR در این مرحله انجام نشده است.
